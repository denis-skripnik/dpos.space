# Android release notes and packaging

## Local main-thread storage/ANR repair (not published)

- Device diagnostics show bridge requests and lifecycle work delayed while checkpoint recovery is active. No Android ANR trace was supplied, so the exact physical-device ANR cause remains unproven. Deterministic JVM tests reproduce main-thread blocking on the shared checkpoint authority and on an ordinary synchronous preference commit; neither test performs a real RPC or broadcast.
- Application version-log initialization, activity cache-version preferences, bridge storage/status/report work and service bootstrap/start/stop/destroy logging now run off main. One process-owned storage queue orders lifecycle and bridge persistence across activity/service recreation; RPC executes on separate workers, never on that queue. `getAppInfo` is cheap metadata and does not request worker status. Request/completion logging cannot hold the UI callback. Foreground channel creation/notification admission, UI replies, consent dialogs and document pickers stay on main; event-inbox migration is separate from foreground notification admission.
- Stop and validated disables invalidate in-memory run tokens immediately, before queued persistence or any store lock. A pending revocation bars new sends as well as old runs until the requested disable is durably stored. Failed persistence remains fail-closed in this process, with an error response and diagnostic/status access still available; a restart does not invent a successful revocation. Full auto-upvoter sync includes implicit revocation of omitted rows. Closed/superseded activities cannot add grants; their revocation subset still persists. Tokens recheck generation after a potentially blocked permission read. Captured activity/service admission follows the run into the runner and its existing child-drain/no-overlap contract. Approved manual Minter/Decimal transfers retain the captured permit across secure-key reads and signing and recheck it immediately before transport, so Stop, validated disable or activity close fences a late send. Once transport has started, its submitted/error outcome is preserved rather than relabeled as an unsent cancellation.
- Lifecycle handoffs preserve effects as well as cancellation: an activity records the cache-version marker only after its live UI actually clears the cache. A service run's token is revoked for sends, but future timer scheduling uses the still-live service owner and fresh background settings reads, so disabling one feature does not strand the rest of an enabled service. Stop/destroy still fence that owner's callbacks, and the next tick gets a new token and revalidates storage. UI launch failures (including unavailable battery settings) return one structured reply rather than escaping the UI handler.
- Boot restore is also a main-thread receiver entry: it now hands storage work off with `goAsync()`. An eight-second receiver deadline finishes the pending broadcast and invalidates late service admission rather than moving a checkpoint wait into a broadcast ANR. An enabled, verified worker still requests the same visible foreground service; expiry does not clear saved settings. Selected diagnostic-document IO has a separate activity-owned writer so a slow document provider cannot monopolize worker persistence; destruction and late callbacks finish at most once.
- Every actual checkpoint read, transaction write, verification, immutable backup and fsync remains synchronous on its background caller. This is not a checkpoint authorization cache or an unordered `apply()` replacement. UNKNOWN/noReplay, exact transaction identity, archive/fence/recovery policy, intake/source cursors, counters and donation contracts are unchanged. Tests retain poisoned-preference/bootstrap refusal checks and use archive-only fixture contention, not valid production keys or live broadcasts.
- Native inbox files/events and total unread counts are retained. The inbox's `MAX_RETAINED_EVENTS = 100` bounds stored event cards, not the separate total unread counter; a large unread total is not proof that the same number of event files is retained. No day-based inbox retention, history pruning, archive optimization, key/state migration or permission change is introduced. The separately scoped updater-only stale-APK policy is documented below.
- Final local 3.1.6/code84 verification: serialized canonical Debug and Release unit gates each passed **466 cases / 70 classes**, zero failures/errors/skips, with identical `(classname, name)` identities. The manual-transfer/boundary safety slice passed **95 cases / 16 classes per variant**, including 18 new real-crypto transfer cancellation/control cases; all five `v3-android-*.js` source smokes passed. Preserved baseline stacks reproduce bridge construction/logging, ordinary-commit and archive-only contention, application/activity/service/boot entry points, and the real service completion UI callback re-entering checkpoint status on main. Later RED cases also caught lifecycle cache-marker, completion-cadence, UI-launch and late-transfer handoff regressions before the final gates. These are JVM/source checks, not physical-device ANR or TalkBack acceptance.
- A local non-debuggable Release APK 3.1.6/code84 was assembled and verified with the historic application ID/certificate and original updater public pin. It is a private verification candidate, not a published signed-feed release. Physical-device unlock/resume, installer/data continuity and TalkBack acceptance remain unverified; install over the existing app without uninstalling or clearing data.

## Local updater repair (not published)

- Download has a visible percentage dialog and Cancel; the message is a polite accessibility live region. Preparation and pre-install verification have visible checking states. The APK stays private at `filesDir/updates/<attempt UUID>/<release filename>`, not system Downloads. A completed transfer shows `Обновление загружено` with an explicit `Установить` action.
- `MainActivity.onResume/onPause` gates updater UI and installer handoff. Pausing cancels active IO, dismisses updater dialogs and prevents late installer launches. Returning during cancellation still offers a retry when it completes. Destroying/recreating the activity cancels its attempt and removes only its own unhanded-off files; a new activity has independent staging, so an old callback cannot overwrite/delete its candidate.
- Android requires `REQUEST_INSTALL_PACKAGES` and the user's per-app permission. Install opens the per-app unknown-sources settings screen when needed; on return, even if permission was denied, the verified candidate remains available. Grant permission and press `Установить` again. Settings/installer launch failures are visible and retryable; no automatic or silent installation is performed.
- Signature, immutable Git provenance, exact SHA-256/Git-blob hashes, real PackageManager APK package/version/certificate identity, observation delay, rollback clock and revocation checks remain mandatory. Installation revalidates the retained file after a settings round trip. Network, hashing, APK/provider/filesystem checks, cleanup and synchronous preference persistence run off the UI thread. Rollback-clock transactions are serialized across overlapping activity instances. Socket disconnect is off the UI thread. Preparation, metadata and streamed reads share a five-minute monotonic operation deadline, checked before/after reads; individual read timeouts shrink to the remaining deadline.
- After successful installer handoff its private file is retained even if the activity is destroyed, because Android may still read the granted URI. Process-owned staging leases now also protect it from later retry-validation failure and stale cleanup; the conservative reservation is made on IO before posting the installer intent, so a cancelled/failed launch may retain extra files rather than risk deleting a granted URI. No installer-completion inference or timeout releases that reservation in this process.
- Connected Robolectric tests use a synthetic Ed25519-signed feed/network/APK payload and controlled PackageManager archive metadata. They execute production parsing/provenance/hash/identity code, with the public certificate from the retained shipped APK, not a production identity bypass. Coverage includes successful explicit handoff, all archive identity fields, installed certificate, permission denial/return/grant, file tampering, launch failures/retry, accessible progress/cancel, pause and rapid resume, old/new recreation overlap and slow-drip total timeout. They do not perform a real APK install.
- These are local source changes only. JVM/Robolectric checks do not prove the reported physical-device freeze is resolved. An already installed old updater cannot acquire this fix without installing a repaired APK over the existing app; never uninstall or clear application data. Before sharing a candidate, independently build/review from the current signed release's source, preserving package/certificate and the real updater public pin; physical-device installer, data continuity and TalkBack acceptance remain separate gates.

## Local private stale-APK cleanup (not published)

- Private verification build: **3.1.7 / code85**. Final canonical Debug and Release unit gates plus Release assembly succeeded; each variant passed **507 cases / 71 classes**, with identical test identities and zero failures/errors/skips. Focused updater/cleanup gates passed 76 cases / five classes per variant. Independent destructive-scope review and narrow budget-fix rereview accepted the documented policy. All five Android JavaScript smokes passed. The final APK retains the historic package/certificate and original updater public pin; no public signed-feed release was made.
- The user reports that private 3.1.6 works on his phone. Physical-device cleanup and TalkBack acceptance of 3.1.7 remain unverified. Install over the existing app without uninstalling or clearing data. Recent APKs and ambiguous partials intentionally remain; this feature does not promise exhaustive reclamation.

- `NativeUpdater.onResume()` automatically submits one coalesced pass to the dedicated process-owned `dpos-update-reclaim` executor. Main does no filesystem/archive work, never acquires the staging mutex and never waits for cleanup. Cleanup does not use the native storage/checkpoint queue, RPC executor or updater network worker. Each pass streams at most 64 directory entries, checks at most four APK archives and stops between calls after a 250 ms monotonic budget. A single filesystem/PackageManager call cannot be forcibly bounded; a slow one can delay background staging claims, never UI or storage/RPC work. Large ambiguous inventories may remain indefinitely; safety takes priority over exhaustive reclamation.
- The only historical candidates are exact `dpos-space-<numeric major.minor.patch>.apk` leaves directly in `filesDir/updates`, or the sole leaf inside one canonical lower-case UUID attempt directory. PackageManager must identify the installed historic-certificate application and the archive must have that same package/certificate, an exact filename/versionName match, a positive versionCode **strictly below the actually installed versionCode**, and a positive last-modified timestamp at least seven days old. VersionCode is the upgrade authority; current/future codes always remain regardless of age. Strict installed upgrade plus the seven-day grace is the historical unknown-handoff policy, not a guess that an installer finished. Recent/future-dated, unknown/unparseable, wrong-identity and partially downloaded historical files remain.
- All legitimate updater instances share one private single-process namespace mutex for claim/create/remove/lease changes and cleanup. A UUID attempt is claimed on background IO before download; `CREATE_NEW`/no-follow output refuses unknown existing leaves. Leases span active writing, READY/permission retries and installer reservation across activity overlap. Only a positively owned unreserved attempt may remove its own partial on cancellation/error/close; unknown partials are not adopted. Installer reservations remain for the process lifetime, including after activity close. After process death, only the strict historical upgrade/grace rule can reclaim complete eligible APKs; current/future files still remain.
- Checks require canonical paths, no-follow regular-file/directory identity and one hard link; identity, size and mtime are checked again after archive inspection. Symlinks, hardlinks, special files, unknown subdirectories, noncanonical UUIDs, multi-entry/ambiguous attempts and permission/identity failures are retained. Cleanup deletes only the verified leaf and, if now empty and identity-stable, its recognized attempt directory. It never deletes the updates root, recursively walks unknown trees, or touches other app files, preferences, keys, inbox, transactions or system Downloads. Existing empty/unrecognized historical directories are left alone.
- Trust boundary: `filesDir/updates` is app-private, all legitimate writers use these leases, and the app has no separate-process updater. Unexpected identity changes fail closed. Path checks followed by unlink are **not** an atomic inode-conditional deletion guarantee against a malicious same-UID/root process rewriting app-private files; such a writer is outside this ownership model. No broader filesystem framework or sandbox claim is introduced.
- Tests use actual private fixture files and API26/API34 Robolectric PackageManager archive identity fixtures, including the historic public DER certificate. They cover the connected automatic resume path, flat/UUID old APKs, active/READY/installer/overlap leases, retries after handoff, actual symlinks/hardlinks/FIFO, parent/leaf swaps, permission denial, unknown data and bounded large inventories. A held cleanup boundary exercises real updater resume, main-looper heartbeat and an independent updater network worker while staging claims serialize. These are JVM checks, not physical-device cleanup, ANR or TalkBack acceptance.

## Secure release-signing diagnostics

- The trusted `dpos_release_sign` consumer writes `dpos-release-sign-attempt.json` inside its operator-private key directory. The atomic mode-0600 receipt contains only public release identifiers, a random attempt marker, timestamps and a fixed outcome code. It never records the submitted secret, secret characteristics, raw signer output or exception text. An unsafe receipt target prevents signing.
- Signer CLI failures return only `status: failed` and an allowlisted `code`. `key_decrypt` means that loading the encrypted signing key failed; it does not distinguish an incorrect password from damaged or incompatible key data. Other codes identify source/dependency checks, subprocess/protocol failures, output verification and receipt/manifest writes.
- The receipt is diagnostic evidence, not proof of successful publication. If an operation returns `unknown`, inspect the matching attempt and independently verify any resulting manifest before retrying. A final receipt-write failure can occur after manifest creation. A consumed operation cannot be reused; a new operation has a new attempt marker.
- The consumer selects the signer interpreter **at operation binding**, using the installed `pm.environments.project_python(root)` API, with `root` taken from that installed module's `__file__` parent-parent. This resolves Hermes's selected dependency environment, not the DPoS repository or a model-supplied path. Keep the returned `venv/bin/python` path intact: resolving its symlink to the PM tools/base Python loses the venv's dependencies. A Gateway can have activated dependency module paths while `sys.executable` still names that bare Python; neither `sys.executable` nor PATH lookup is a valid fallback.
- Before returning either init/sign `BoundOperation` (and therefore before Secure ENV can issue its password form), `signer_python()` runs a bounded, secret-free import preflight for the signer's `cryptography` serialization/Ed25519 modules under exactly the signing subprocess's stripped environment (`PATH=/usr/bin:/bin`, `PYTHONNOUSERSITE=1`). Stdin/stderr are discarded; only a fixed stdout readiness marker is accepted. No key path, key read, password, signer request or receipt is involved. Selection/import/executable/timeout failures refuse binding with only `signer_runtime`, never raw output or exception text. No receipt is created for a pre-binding refusal. This is an import readiness check, not a guarantee against later runtime removal or same-UID tampering.
- Each returned callback closes over that preflighted interpreter path. Registering factories does not freeze a runtime, and changing PM selection or `sys.executable` after binding cannot redirect an already bound callback. Source, immutable APK, signer dependency pin, encrypted-key, receipt, public trust and signature checks are unchanged. No package installation or new configuration/model parameter is required; a missing PM runtime fails closed rather than falling back to system Python.
- Run the original 27 synthetic signer/consumer cases and five runtime regressions with the installed Hermes dependency Python from the repository root: `python -m unittest discover -s tests -p 'test_release_[rs]*.py' -v`. Runtime tests require the existing Hermes PM installation and its dependency-free base interpreter; no dependencies are installed. They launch that real base interpreter with the gateway-style owning-install PM module plus activated dependency module paths, initialize only a temporary synthetic encrypted key, execute the actual signer subprocess through the selected venv, and independently verify the signed fixture and tamper rejection. Other cases cover binding-time freezing, missing/non-Python/dependency-free runtimes, selection/timeout errors, and secret-free stripped-environment preflight. These are local synthetic signing checks, not a production signing attempt or publication proof.
- Activate code changes only after independently reviewing the consumer and unchanged signer pin, updating the operator's trusted consumer digest, and performing the supported handler reload/bootstrap in the owning Gateway. Do not derive a replacement trust pin from unreviewed adjacent code. APK bytes, existing keys, signed-feed policy and signature/provenance checks remain unchanged. Tests do not change configuration, keys, forms, Gateway state or deployed code.

Fresh release APK SHA-256 `02656c63c2b9aa2dde09e7b3e366d975c5a5551a9b00b9755e360a82c68e1cd6` verifies historic package/certificate, updater pins, non-debuggable manifest and HTTPS-only policy. On API35/KVM, both full checkpoint/runtime/Golos restart runs passed: eight phases per run with distinct process PIDs, retained fence/incompleteness and no uncertain-send replay. This is synthetic local-RPC runtime evidence, not live-chain, full UI or TalkBack acceptance.

- Compatible candidate uses the existing `space.dpos.android.debug` package and historic certificate while remaining a non-debuggable Release build. The `.debug` package suffix is historical identity, not permission to ship debuggable networking. Build with the protected existing owner public updater pin; verify the APK itself, certificate, package, manifest and hash before delivery.
- The native `legacyIdentityIncomplete` flag is retained permanently as evidence, not as a permanent global send hold. A fresh endpoint-bound fence is checkpointed; adoption waits for height+1 <= LIB, canonical next-header.previous == saved head ID and irreversible chain time beyond the conservative observed-time+3600+120-second drain. Requests are monotonic-bounded and head age must be <=120 seconds (<=15 seconds future skew). Stale endpoints defer/retry; they do not erase the fence or declare network-wide stoppage.
- Fallback is selected before energy planning and intake as well as before the proof, and pinned across energy/account reads, history, config, head, headers, content, own vote, authority, signature, transport, immediate confirmation and fresh dependent donation. A stale high-energy peer must not supply the budget for a fresh low-energy peer's vote. Endpoint failover must independently validate the saved canonical anchor; no cutoff regression. Golos HTTP redirects are not fence proof. Android elapsedRealtime includes suspend; monotonic deadlines are never restored as permission from disk. Late preparation checks the unchanged signed header against fresh chain/local time and may cancel only a current proven-unsent intent, never an attempted/legacy unknown.
- Only exact root generations with valid consensus id/root/created strictly after cutoff and created <= canonical LIB timestamp are eligible. Content generation/revision is checked before signing and again after durable preparation just before transport. All identifiable unknown author/permlink guards remain across weights/kinds and generations. Old roots, edits of old roots, equal cutoff and reversible creation remain excluded.
- Backlog disposition is separate from intent authority: proven pre-cutoff generations are terminal policy skips, and redundant candidates for archived targets are acknowledged without deleting their intent/quarantine or inventing a receipt. Otherwise old/unknown rows could fill intake capacity and indirectly starve arbitrary future targets. Retired cached fence metadata is copied into immutable import evidence but never activated as a fresh checkpoint fence. Fence records include initial LIB and verified canonical LIB/time/adoption observations; generation records retain LIB height/time and a content revision digest, and support status retains the incomplete-identity flag alongside the canonical fence.
- Boundary: deleted/recreated UNKNOWN old textual addresses and names lost on orphan forks can pass as new canonical generations. This is not recovery of those names, first-ever permlink proof, cryptographic state proof or an atomic generation-bound vote. The protocol carries only voter/author/permlink/weight, so final-read/execution TOCTOU remains.
- Stop/consent, normal energy and cashout policy, durable PREPARED/attempted noReplay and exact-ID canonical finality remain unchanged. Recovery does not manufacture receipts, counters or donation catch-up. Donations follow only newly confirmed allowed votes through the existing durable contract.
- New JVM loopback tests exercise the real signer/HTTP/checkpoint/runtime. `GolosRecoveryAndroidTest` supplies a synthetic-RPC A/B/C distinct-PID Android boundary harness. The full `--include-golos-recovery` driver passed twice on the separately approved disposable API35/KVM host; each run includes checkpoint A/B, runtime A/B/C and Golos A/B/C. Its 14 JUnit invocations include phase-only early returns and are not 14 independent scenarios. Prior checkpoint-only evidence remains in `dpos-hostkey-20261014/FINAL-R2.md`; final lane evidence is under `dpos-hostkey-20261015/`. Real-chain availability, physical-device data continuity and TalkBack remain unverified.

Build debug APK:

```bash
cd android
./gradlew clean test assembleDebug
sha256sum app/build/outputs/apk/debug/app-debug.apk
```

CI:

- `.github/workflows/android-debug.yml` runs on branch `v3` for Android/workflow changes.
- The workflow runs `./gradlew test`, `./gradlew assembleDebug`, writes `app-debug.apk.sha256`, and uploads the unsigned debug APK as an artifact.
- The workflow does not use signing keys, Play service accounts, or release passwords.

Release signing plan:

1. Generate or use an existing Android keystore outside this repository.
2. Provide signing config through local untracked Gradle properties or CI secrets.
3. Never commit `.jks`, `.keystore`, key passwords, Play service accounts, or upload keys.
4. Name manual artifacts as `dpos-space-android-<version>.apk` and publish checksums next to them.

Manual smoke checklist before sharing an APK:

1. Install debug APK on Android device/emulator.
2. Launch app and verify DPoS Space WebView opens `https://dpos.blinddev.xyz/`.
3. With TalkBack, confirm main route navigation remains usable.
4. From WebView console/debug UI, call `getAppInfo()`, `getWorkerStatus()`, `importWorkerSettings()` with explicit non-secret Golos settings, `importSecureKey()` with a controlled test-only key on a non-production device, `previewAutoVote(json)` for a known harmless candidate, `startWorker()`, `checkNow()`, `stopWorker()`, `exportWorkerLogs()`.
5. Verify `importWorkerSettings()` rejects secret-like fields and `importSecureKey()` returns only `keyRef` / `hasKey` metadata without echoing the imported secret.
6. Verify `previewAutoVote(json)` returns `broadcasted: false` and never submits a transaction.
7. Verify the foreground notification is visible while running and has Open / Check now / Stop actions.
8. Verify exported logs are redacted and do not contain private keys, seeds, WIFs, passwords, tokens or raw encrypted blobs.
9. Reboot the device/emulator after enabling the worker and confirm boot restore either resumes the visible worker state or reports why Android restrictions prevented it.
